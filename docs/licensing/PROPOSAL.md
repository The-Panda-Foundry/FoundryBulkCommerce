# Proposed ARR / LGPL3 section4(d)(0) compliance route

26 November2026. **DRAFT FOR OWNER APPROVAL. Not adopted licence terms, not legal clearance.** Official version0.2.3, transaction behaviour and strict native fingerprints remain unchanged. No binary is built/released by this proposal.

## Recommended approach

Treat the LGPL-linked runtime conservatively as a Combined Work for compliance planning. Retain ARR over independent Foundry application code, with the explicit limited recipient permissions drafted in PROPOSED_EXCEPTION.md. Use section4(d)(0), not a claim that the current official binary satisfies section4(d)(1). Provide complete Corresponding Application Code, required Minimal Corresponding Source and build/installation information using a durable source distribution alongside each official binary, with clear access directions at the binary's download location. Plan an equivalent-access network distribution under GPL3 section6(d); a repository homepage link alone is insufficient if exact sources/materials cannot actually be obtained. Retain an immutable release source package/version mapping and ensure third-party-hosted required material remains available; establish an owner archival/continuity plan where redistribution is legally permitted.

Official pins remain exact and fail closed. A recipient who lawfully modifies an LGPL library can rebuild their own application copy with explicitly selected exact replacement digests and compatible APIs, using the instructions in REBUILDING.md. This proposal does not add a wildcard, flag or trust bypass to the official addon. Public source under ARR alone is insufficient: the permissions and the actual usable rebuild materials must accompany it.

## Permissions that need approval

Permit copying necessary application/build material, inspecting/debugging, modifying the application as needed for lawful library modification/recombination (including local digest changes and Mixin compatibility adaptations), recompiling, installing, running and conveying resulting recombined copies and necessary materials to recipients exercising those rights. The permission must not stop at private use, non-commercial use, or a discretionary request for approval for each recipient. Preserve applicable downstream rights and notices; separate branding/endorsement from those rights. Draft exception is deliberately not an upstream licence grant. Whether the exact final language and scope satisfy LGPL requires legal review before adoption; no claim that all independent application material must itself be relicensed LGPL is made.

## Runtime Mixins and library-derived material

BankAccountAccessor causes generated accessors to be added to loaded Numismatics BankAccount. TreasurySellAllMixin changes loaded Treasury handler control flow. Thus original native JARs are unmodified on disk, but runtime classes are transformed. Curios is an API-only bridge with no Curios Mixin. Do not describe this as no upstream modification of any kind.

The prior26-current-file/60-historical-version/83-reference-file comparison found no copied implementation body. That supports independent application code, not conclusive legal classification of runtime transformations. Under a conservative modified-library analysis, any library-derived transformed portions and corresponding changes must retain applicable LGPL rights. The short accessor declarations may remain application interoperability code, but the owner must determine whether those declarations/transformation material need an explicit LGPL grant. Do not place protected upstream bodies under ARR. No transformed native class files are distributed. Provide the actual Mixin inputs/configuration and native source/build route needed to reproduce any relevant transformation; independently authored transaction/ledger code is not thereby automatically LGPL.

LGPL section2(a) must also be assessed if a modified library facility calls application-supplied code: the Numismatics accessors are field reads/writes, while the Treasury callback delegates to the application but Treasury's exact rights are disputed. No unsupported conclusion that every Mixin forces all Foundry code to GPL is made. SPDX/GNU texts and actual code, rather than packaging labels, control the analysis.

## Current viability and blockers

**Plausible conditional route; not yet a demonstrated complete compliance solution.** Known obstacles: final exception not adopted; Curios9.5.1 candidate source commit identified but source-to-artifact/build reproduction not established; Numismatics candidate commit/license/properties and BankAccount source header verified but upstream build reproducibility/source completeness not independently demonstrated; required native/transformation source distribution still needs review; Treasury permission discrepancy unresolved; end-to-end recipient modified-library rebuild not performed. Restricted external non-LGPL compile references must be legally obtainable and their API/source treatment reviewed; the manifest does not grant permission to redistribute native JARs. An arbitrary moving branch or decompiled source is not an adequate substitute for exact corresponding source.

Changing reference digests in a recipient's own copy does not prove the replacement is transaction-safe. It must remain exact, be inspected and tested; the owner is not obliged to endorse/support the fork. Do not condition LGPL rights on official approval or successful safety certification. Preserve scope distinctions: safety qualification is operational guidance, not an extra legal restriction.
