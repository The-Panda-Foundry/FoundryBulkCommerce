26 November 2026 — v0.2.3. No deployment is performed or authorised by this package. Production artifact is only `foundrybulkcommerce-0.2.3.jar`; never install Commerce Fixtures, test classes, sources or Git bundles in production.

Back up the complete world/player data, both Sophisticated repositories, Numismatics bank data, configuration and complete SQLite ledger/sidecars consistently. 2. Verify SHA256SUMS in the release artifacts directory. Replace only the old addon with exactly one0.2.3 JAR on an isolated staging server. 5. Perform the acceptance gates below. Retain logs, balances, inventories and transaction references before considering a production maintenance window. This package does not approve that deployment.

## Focused dedicated/integrated acceptance

- Join the staging dedicated server with an original modpack client **without Bulk Commerce**. Check existing Treasury UI, normal native tooltips and backpack/shulker interfaces. Repeat on an integrated host.
- In disposable staging, use native crafting/UI or the separate development-only fixture utility to make upgraded containers. Existing `/bcfixture backpack wheat 300000` creates Netherite/Omega; add other upgrades and configure their resources through the native UI. Keep the utility out of production. Do not use commands that fabricate storage UUIDs/NBT.
- In both shulkers and backpacks: test no upgrades, stack only, every ordinary upgrade used by players, several ordinary upgrades, full upgrade slots and Omega mixed with other upgrades. Add matching wheat to a crafting grid, fuel/cooking inputs, anvil/smithing items, music disc, fluid/energy and configured filters where supported. Photograph/record exact configurations and auxiliary quantities.
- Sell primary wheat in lots2304 at1 Spur. Confirm maximum100 bundles/230400 removed per sale, precise remainder/payment/ledger, installed upgrades/configuration/auxiliary resources unchanged, then repeat to insufficient stock. Test mixed container families and loose items. Protected main/offhand/equipped/nested containers must remain untouched.
- Test blocked inception/compression/infinity/mob catcher configurations and a protected duplicate UUID; only other safe stock may sell. Debug logging distinguishes upgrade/storage rejection from insufficient primary stock. Never weaken identity safeguards to make a test pass.
- Move/change the selected container or upgrade contents during pending preparation; stale plans must cancel without mutation/payment. Busy concurrent requests may be refused by the existing global admission gate; run several players repeatedly and reconcile every successful reference against inventory and bank deltas. No overlapping addon plans should execute.
- Run native automation with ordinary upgrades between requests. Stock/config changes may cancel pending sales; do not expect processing/I/O filters to govern manual primary selling. Verify no upgrade processing/remote/nested extraction is introduced by a sale.
- Save/stop normally, restart and inspect the **same UUID**, primary counts, all upgrade resources/configuration, bank, recent/inspect rows, instance identity and admission. Check tooltip and opened inventory against the canonical contents before/after sale and restart.
- Measure real-host tick/MSPT, request latency, SQLite commit latency, allocation/GC and disk/WAL growth under repeated large mixed upgraded storage and multiple players. Existing limits/cooldown stay enabled; isolated microbenchmarks are not host load certification.
- Only in an isolated disposable clone: interrupt before/after durable intent and economic mutation/outcome, then restart. Check dirty-boot/unresolved containment, read-only evidence and manual reconciliation workflow. No automatic replay/refund is expected. Also validate disk/permission failures safely in staging. A deliberate kill is not part of these automated tests.
